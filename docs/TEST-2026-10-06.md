# vm6747sim on Windows and Linux, against TI's CCS 5.5 C6747 simulator - 2026-10-06

**The simulator tested:** `8c1e130`, built fresh on each box - g++ on the Linux box (Amazon Linux 2023), MSVC 2022 in RIDE 5.0's
solution on the Windows box. **The oracle:** CCS 5.5's C6747 cycle-accurate simulator on each box, through DSS
(`runca.js`), `cycle.CPU` and `cycle.Total` each in its own session. **The programs:** 49 linked `.out` images at -O2 -
20 built by TI's cl6x 7.4.4 with `rts6740_elf_eh.lib`, 29 by cpp11 + ASM6x + LNK6x against the same library - covering
the six kernels, hello/arith/floats/structs, static constructors, exceptions, SP/DP floating point, 64-bit integers and
division, printf, and pipelined (SPLOOP) loops. The same image is handed to both simulators; nothing ran on the Mac.

## Code from CCS 7.4's compiler, cl6x 8.2.2 - 30 of 32

CCS 7.4 has no C6747 simulator: TI dropped the C6000 simulators after the CCS 5 series. What CCS 7.4 adds is its compiler,
cl6x 8.2.2. Every source of the 49 above, plus `virt` and `ctor`, was built with it at -O2 on the Windows box, against 8.2.2's
`rts6740_elf_eh.lib`. `--exceptions` was used for C++ only, since 8.2.2 refuses it for C. Each image was run on vm6747sim
(`60a9a81`) and on CCS 5.5's cycle-accurate simulator (`cycle.CPU`, `cycle.Total`).

## What still fails

- **D5 - exceptions (10 programs):** every program that throws stops in TI's unwinder within ~1,000-4,000 cycles
  (`regb_core_get+16`, a load through a null `_Unwind_Context`) - catch-by-reference, cleanup, throw-class, throw-pointer,
  throw-temporary, temporary-unwind, try-in-try-body; cl6x's and cpp11's alike.
- **D4 - the loop buffer (3 cl6x programs):** `pointer-strides.ti-O2` (16 cycles), `fill-stores.ti-O2` and
  `divide-by-constant-signs.ti-O2` stop on a write conflict from an SPLOOP epilog. cpp11 writes no SPLOOP; its builds of
  the same three pass.
- **D6 - NaN and infinity (new, silent):** `runtime-shapes.cpp11-O2` runs to `C$$EXIT` and prints `0 0 -2 3` where the
  C6747 prints `1 1 -2 3` - `std::isnan(0.0 / 0.0)` and `std::isinf(1.0 / 0.0)` answer 0. Every other floating-point
  result in the 49 matches, so it is the NaN/infinity path: a DP compare that does not treat NaN as unordered, or a
  division that does not make NaN or infinity.
