# Review of VM6747-sim at 43ffc5d, against the CCS 5.5 C6747 cycle-accurate simulator

**Date** 2026-10-05. **Tree reviewed** `/Users/g.r.akhtar/Developer/Claude/VM6747-sim` at
`43ffc5d` ("vm6747 --run: the C674x running machine code - a first cut, to be held to the
simulator's traces"). **Oracle** the Linux box (`ssh ansicc`): CCS 5.5, cl6x 7.4.4 and the C6747
cycle-accurate simulator driven through DSS with `tools/c6747/runca.js` from C++Optimize, one
session at a time, `cycle.Total` (event 0) and `cycle.CPU` (event 1). Nothing in VM6747-sim was
changed; the only file added is this report.

## Summary verdict

**As shipped, the simulator runs no program.** Every one of the 49 images tried (20 built by
cl6x 7.4.4 `-O2`, 29 by cpp11 `-O2` + ASM6x + LNK6x, plus cl6x's own `hello/arith/floats` at
`-O2` and `-O0` from the oracle kit) faults in TI's boot or `printf` path, 2,000-6,000 cycles
in, before `main` has printed anything. Three defects in the pipeline model cause all of it
(D1-D3 below); with three small patches in a scratch copy (not in the repository) 32 of the 49
run to `C$$EXIT` and print, the rest failing in the loop buffer (D4) or the unwinder (D5).

**The oracle comparison is not done.** All 49 images are queued on the Linux box
(`~/simrev/ship/run-oracle.sh all.list`, one DSS session at a time, 25-minute cap per run,
`cycle.Total` then `cycle.CPU` for each) behind Cowork's own `oracle/run.sh` trace job, which
held the box's single DSS session for the whole of this review (its `intrin2`/`structs` traces
were still running at 17:57 UTC; the queue starts itself when that ends). The per-program table
in section 3 is therefore empty in this revision, and no cycle ratio or wall-time ratio is
claimed. Section 2 says exactly how to finish it: the images, the results directory, and
`table.py`. What *was* measured against the oracle is the two complete step-by-step traces the
kit had already produced (`arith.O2`, `hello.O2`): they are what located D2 and D3.

## What the repository is, and what it claims

Four commits. `1c4e918` copies VM6747/Emulator (the assembly-text emulator, whose README is still
the README here and describes *that* program, not this one). `1dfc25c` adds `oracle/`, a kit that
runs TI's CCS 5.5 tools on the two boxes as a black-box reference. `5206761` adds the C674x
opcode table (528 forms of 213 mnemonics, collected from binutils' `tic6x` tables), a
fetch-packet decoder with the compact header, ELF/COFF/hex loaders and `--dis`. `43ffc5d` adds
`--run`: the C6747 memory map, a pipelined CPU (`C6xCpu.cpp`, `C6xExec.cpp`), the loop buffer
(`C6xLoop.cpp`) and the host side (`C6xHost.cpp`: CIO at `C$$IO$$`, the stop at `C$$EXIT`,
`-c`, `--trace`). Its own commit message calls it "a first cut, to be held to the simulator's
traces", and that is exactly its state: **it has not yet been held to them**. The two self-tests
(`tests/c6x-run.sh`, ten hand-timed steps; `tests/c6x-dis.sh`, eight words) pass. Nothing else
in the tree exercises `--run`.

The repository's `build/` holds aarch64-Linux objects and an aarch64 `vm6747.exe`, so a plain
`make` on the Mac fails at the link (`unknown file type in build/obj/*.o`) and the linker removes
the prebuilt root `vm6747.exe` in the process (it is gitignored; I rebuilt a Mac binary there
afterwards). I built into my scratchpad with `make OBJDIR=... BINDIR=...`.

## 1. Code review

### 1.1 Instruction coverage (`src/C6xOpcodes.inc`, `C6xExec.cpp`)

- The table is the C674x set as binutils has it: fixed point (32- and 40-bit, SIMD, saturating,
  the 16x16 and 32x32 multiplies, Galois), C67x floating point (SP and DP arithmetic, the
  conversions, `RCP*`/`RSQR*`, the DP compares), the loads and stores including the non-aligned
  `LDNW/LDNDW/STNW/STNDW`, `SPLOOP/SPLOOPD/SPLOOPW/SPKERNEL(R)/SPMASK(R)`, and every compact
  16-bit form with the header's `RS`, `DSZ`, `BR`, `SAT` and `PROT` bits. `C6xExec.cpp` gives
  all 213 mnemonics a semantics, with `DDOTP4`, `DDOTPH2/L2(R)`, `SHFL3` and the `RCP/RSQR`
  approximations marked unverified. `SWE/SWENR` and `IDLE` stop the run by name; interrupts,
  exceptions and the 40-bit forms beyond the pairs are not modelled.
- The timing data per operand (read cycle, write cycle for the low and high words) is
  binutils', and spot checks agree with SPRUFE8 for the C674x: `DPSP` writes at cycle 4 (three
  delay slots - the recent `C2` defect in our own tools is *not* repeated here), `ADDDP/SUBDP`
  6/7, `MPYDP` 9/10, `MPYSPDP` 6/7, `MPYI` 9, `INTDP` 4/5, `SPDP` 1/2, `CMPxxDP` 2, `MPY32` 4,
  loads 5, the DP sources read low word at 1 and high at 2.
- **`C6xExec.cpp:566-581` (defect D1):** `MVC reg,ILC` in its compact form carries `ILC` as a
  text operand (`C6xDecode.cpp:135`, `O_ilc`), and the MVC case only accepts `Operand::Ctrl`, so
  it falls into the read branch and faults "a result to an operand that is not a register".
  TI's `writemsg` (the CIO path every `printf` ends in) is `SPLOOPD 1 || MVC B6,ILC`, so **every
  program that prints dies at 0x8000df76 in rts6740's `writemsg`** (`hello.O2.out`: `vm6747: at
  0x8000df76, cycle 2553: a result to an operand that is not a register (writemsg+22)`).
- `C6xExec.cpp:145`: `if (block == 0 || block == 0)` is a typo (harmless).
- `toInt` (`:50`) converts a NaN to `0x7fffffff` with a "to be checked" note; SPRUFE8 gives
  `0x80000000` for `SPINT/DPINT` of a NaN - unverified either way, and no program here reaches it.
- `CSR` is initialised to CPU ID `0x14` (`C6xCpu.cpp:34`); TI's simulator reports `0x44010100`
  (CPU ID 0x44, REV 1), with `IER.NMIE` set and `DNUM = 1` at main. Cosmetic until a program
  reads them.

### 1.2 Pipeline and delay slots (`C6xCpu.cpp`)

The model is a scheduled-write list (`writes_`), a per-register history for reads in earlier
cycles (`hist_`), executes deferred to the cycle of the last source read (`execs_`), memory
operations in E3 (`memops_`), branches landing after five cycles, and NOP holds. Two timing
rules are wrong, and the oracle's traces show both:

- **D2 - store data is read in E3, not E1.** `issue()` skips the data operand of a store when
  computing its read cycle (`C6xCpu.cpp:267`) and `cycleEnd()` reads the register when the store
  reaches memory (`:165`, cycle E3). On the C674x every source is read in E1. cl6x's idiom for
  a call, `STW B3,*B15--(8) || CALLP f,B3`, therefore pushes the *new* B3 instead of the old one:
  in `__TI_eb_init` (every image linked with `rts6740_elf_eh.lib`) the function returns to
  itself, pops one word further each time, and jumps into `.far` - the fault at
  `__c6xabi_extab$__cxa_call_unexpected+12` on all 20 cl6x images and all 29 cpp11 images.
- **D3 - the pre/post-increment of a load's or store's base register lands in E3, not E1.**
  `memop()` runs at the memory operand's read cycle (3) and schedules the base update with
  `writeReg(m.base, nb, x.issue)` (`C6xExec.cpp:194`), which `land()` only applies at the end
  of that E3 cycle. Hardware updates the base at the end of E1, so a consecutive-cycle
  `LDW *++B15(8),B13; LDW *++B15(8),B11:B10` reads a stale B15. TI's `hello.O2` trace shows B15
  stepping by 8 on every packet through an epilogue (steps 467-469, `0x80008bc90..bc98`) while
  the simulator's B15 lags one packet; the restored A12 and B10 are wrong at `0x8000b414` and
  the program derails. Same at `[A0] LDB *A4++[1],A3` in `_printfi`'s strlen (TI step 56-57 vs
  simulator step 1099-1100 of `arith.O2`).
- Branches, NOP holds, `BNOP/CALLP/ADDKPC` folds, `PROT` loads and the write-conflict fault
  are modelled as SPRUFE8 describes them, and the register history makes the DP split-phase
  reads come out right. Neither the cross-path stall (one cycle when a cross path reads a
  register written the cycle before, C64x+/C674x) nor the functional-unit latency of the
  multi-cycle DP instructions is modelled; both affect `cycle.CPU`, not results, and cl6x
  schedules around the second.
- `-c` counts from the entry point (`C6xHost.cpp:230`), where TI's simulator (after
  `loadProgram`, which runs to `main`) counts from `main`. The boot - `_c_int00`, the `.cinit`
  decompression, `__TI_cpp_init` - is 1,650 cycles for the non-EH rts, 2,113-2,126 with
  `rts6740_elf_eh.lib`, and 17,000-90,000 for a program with static constructors. The tables
  below subtract the simulator's own entry-to-`main` cycles.

### 1.3 The loop buffer (`C6xLoop.cpp`)

The model is the assembly emulator's, ported to decoded instructions: load at LBC, replay every
`ii`, ILC at the stage boundary, `SPLOOPW`'s predicate three cycles back, `SPKERNEL fstg,fcyc`,
`SPMASK`, reload. It runs cl6x's loops in `writemsg`, `_printfi` and the kernels (once D1-D3 are
out of the way), but with the reviewer's patches in place three cl6x `-O2` images still fail
inside `SPLOOP` regions:

- **D4** `divide-by-constant-signs.ti-O2.out`: "two results land in B4 in one cycle (SPRUFE8
  3.8.8): from 0x80000b40 and 0x80000bb4" - `SHRU.S2 B7,1,B4` is a kernel instruction
  (the loop ends `SPKERNEL 1,0` at 0x80000b9a) and `MVKH B4` at 0x80000bb4 is the program after
  `NOP 7; B; NOP 1`. On hardware the epilog has drained before the MVKH issues; the simulator
  replays the kernel instruction one stage too late, so the epilog length or the
  `SPKERNEL fstg,fcyc` fetch delay is wrong for this shape. cl6x's code is correct, so the
  fault is the model's.
- `fill-stores.ti-O2.out` branches to 0x81e8cd3d and `pointer-strides.ti-O2.out` stores at
  0x00000024 (`main+174`), both inside `SPMASK`-heavy loops; not isolated further.

### 1.4 Loader, CIO and exceptions (`C6xImage.cpp`, `C6xHost.cpp`)

- The ELF loader takes every `SHF_ALLOC` section, loads PROGBITS, leaves NOBITS; cl6x's ROM
  model (`.cinit` decompressed by `__TI_decompress_rle24`/`lzss` at boot) therefore runs as on
  the part, and with D1-D3 patched the decompressed `.neardata`, `.fardata` and `.rodata`
  matched what cl6x put in the record (checked byte by byte for `float-literal-exact`).
- `addSymbol` (`C6xImage.cpp:42-50`) keeps the first non-temporary name at an address, and TI's
  `__TI_exidx_linkto_scn_start_N` symbols alias every function start, so faults are reported
  against those names rather than the function (`__TI_exidx_linkto_scn_start_40+116` for
  `malloc`'s neighbourhood). Cosmetic, but it makes every diagnostic harder to read.
- CIO (`C6xHost.cpp:58-134`): `open/close/read/write/lseek/unlink/rename/getenv/time/clock`
  are served at the `C$$IO$$` breakpoint from `_CIOBUF_`, stores flushed first. Correct for
  stdout/stderr; `DTGETCLK` answers the CPU cycle count. With D1 patched, `printf` through
  `writemsg` prints what TI's CIO prints on every program that reaches it.
- **D5 - exceptions do not run.** Every image that throws (cpp11's `throw-class`,
  `catch-by-reference`, `cleanup`, `temporary-unwind`, `throw-pointer`, `throw-temporary`,
  `try-in-try-body`, and cl6x's `throw-class`, `catch-by-reference`, `cleanup` built with
  `--exceptions`) faults in rts6740's unwinder: `a 4-byte load at 0x0000002c ...
  (_Z13regb_core_getP15_Unwind_Context14_Unwind_Reg_IdPj+16)` - `regb_core_get` is handed a
  null `_Unwind_Context`. The last global before the fault is
  `__TI_targ_unwind_regbuf_setup`. Not isolated further; it reproduces identically on cl6x's
  own build, so it is the CPU model and not the compiler.

### 1.5 Cycle accounting against `cycle.Total`

The memory system is not modelled at all: no L1P, no L1D, no write buffer, no EMIF timing;
`Memory` is flat pages with every access free. What the simulator counts is the issue schedule,
i.e. TI's `cycle.CPU` without the cross-path stall. The C6747 program here runs from the 128 KB
shared RAM with the caches as the simulator leaves them after reset, so TI's `cycle.Total` is
dominated by `CPU.stall.mem.L1D` and `L1P` - 2 to 6 times the CPU count on the kernels (see the
table). The new simulator cannot be compared with `cycle.Total` for performance work until it
has a memory model; what it can be compared with is `cycle.CPU`, and the table has both.

### 1.6 The oracle kit (`oracle/`)

- `remote/trace.js:46` writes a negative register as a 16-digit sign-extended string
  (`ffffffff8000aee4`), and `compare-trace.py:40` strips with `lstrip('0x')`, which also strips
  leading zeros - so no high-bit value ever compares equal and the kit reports every step as a
  difference. (My comparison normalises to the low 8 digits.)
- TI's trace steps one *cycle* at a time (a `NOP 5` is six lines at one PC) and the
  simulator's `--trace` one *execute packet*; `compare-trace.py` zips them line by line, so even
  a perfect CPU would disagree from the first hold. `C6xCpu::drain()` exists but `--trace`
  never calls it, while a halted TI simulator shows landed results - another systematic
  difference the kit does not account for.
- `gen-words.py` writes `.word` data into `.sect ".text"`, and cl6x 7.4.4 then gives the
  section no `SHF_EXECINSTR`: `dis6x` lists all 32,768 words as `.word 0x...` and the vm's
  `--dis` lists nothing for the object (the section is not code) until `--all`. The decoder
  corpus therefore holds the decoder to nothing - `compare-dis.py` reports 5,277 of 32,768
  "agreeing", those being the words both print as data.
- `compare-dis.py`'s normal form does not cover dis6x's spellings (`$C$L25 (PC+160 = 0x...)`
  targets, `*B7[4]` scaled offsets, `MV`/`OR 0`, `ZERO`/`SUB`, `||^`), so on a real image
  (`arith.O2.out`, 7,671 instructions) it reports 3,262 agreeing; the disagreements I read are
  all spelling. The decoder decoded every instruction of the 49 images here that the CPU
  reached, and the listing of `writemsg`, `_printfi`, `__TI_eb_init` and the rle24 decompressor
  agrees with dis6x instruction for instruction.
- `oracle/run.sh` ships TI's `C6747.cmd` and a copy of the two ccxml; it builds with
  `rts6740_elf.lib` (no exceptions), where every C++ program this tree links uses
  `rts6740_elf_eh.lib` - the D2 path (`__TI_eb_init`) is only reached with the EH library,
  which is why the kit's six C programs could never have found D2.

## 2. Method for the measurements

- Images: `tools/c6747/bench` (fib, hash, isort, matmul, sieve, virt), `tools/c6747/programs`
  (hello, arith, floats, structs), `tools/c6747/ctor`, and 22 cases from `C++Optimize/tests/cases`
  (throw-class, throw-pointer, throw-temporary, catch-by-reference, cleanup, temporary-unwind,
  try-in-try-body, lifetime-ledger, dynamic-init, virtual-dtor, narrowing-allowed,
  float-literal-exact, long-double-exact, runtime-shapes, divide-by-constant-signs,
  longlong-shift-runtime-count, stream-char-types, stream-long-long, pipelined-loops,
  hoisted-invariants, pointer-strides, fill-stores). cpp11 `-O2` builds of all 29 (ASM6x
  `--compress`, LNK6x `--cgt=7.4.4`, `C6747.cmd`, `rts6740_elf_eh.lib`, heap/stack 0x800), and
  cl6x 7.4.4 `-O2` builds of the 20 that cl6x accepts (`--exceptions` for the three that throw),
  linked by lnk6x 7.4.4 the same way. The same `.out` goes to both simulators.
- The oracle run: `runca.js` with event 0 (`cycle.Total`) and again with event 1 (`cycle.CPU`),
  stdout through CIO logging; results land in `ansicc:~/simrev/ship/res/<image>.{total,cpu}.result`
  and `.total.stdout`. Copy `res/` to the scratch work directory and run `table.py` there
  (it reads `out/*.vm.result`, `boot2.txt` for the simulator's entry-to-main cycles, and
  `vmtime.txt` for best-of-three wall times) to produce section 3.
- The simulator side was run on the reviewer's patched build (D1-D3 applied, a store watch
  under `VM_WATCH`), since the shipped binary completes nothing. Output comparison must be
  against the oracle's stdout for the same image, not `.expected`: cl6x 7.4.4 folds
  `float-literal-exact`'s literal to 1.0 (its `.cinit` record holds `3ff0000000000000`), so the
  simulator's `0 1 5` for that image is cl6x's answer and clang's `.expected` does not apply.

## 4. Defects, ranked

1. **D2 (fatal, every program)** - store data read in E3 instead of E1. `C6xCpu.cpp:267` and
   `:165`. Reproducer: any image linked with `rts6740_elf_eh.lib`, e.g. `fib.ti-O2.out`:
   `vm6747 --run fib.ti-O2.out` -> `an undefined instruction word (__c6xabi_extab$__cxa_call_unexpected+12)`;
   `--trace` shows `__TI_eb_init` (0x80008840) returning to itself after
   `STW B3,*B15--(8) || CALLP malloc,B3`.
2. **D1 (fatal, every program that prints)** - compact `MVC reg,ILC` faults. `C6xExec.cpp:566`.
   Reproducer: `vm6747 --run hello.O2.out` (oracle kit image, non-EH rts) ->
   `at 0x8000df76 ... a result to an operand that is not a register (writemsg+22)`.
3. **D3 (silent wrong results)** - a load/store's base-register pre/post-increment lands in E3.
   `C6xExec.cpp:194` (scheduled from the E3 execute). Reproducer: with D1 patched,
   `vm6747 --run hello.O2.out --trace t` against the kit's `hello.O2.trace`: B15 lags from
   TI step 467 (`0x80008bc90`), A12/B10 wrong at `0x8000b414`, no output.
4. **D5 (exceptions)** - the unwinder is handed a null `_Unwind_Context`:
   `vm6747 --run throw-class.ti-O2.out` (patched build) -> `a 4-byte load at 0x0000002c ...
   (regb_core_get+16)`. Same on every throwing image, cl6x's and cpp11's.
5. **D4 (loop buffer)** - the epilog of an `SPKERNEL 1,0` loop overruns into the program:
   `vm6747 --run divide-by-constant-signs.ti-O2.out` (patched build) -> `two results land in B4 in
   one cycle ... from 0x80000b40 and 0x80000bb4`. `fill-stores.ti-O2.out` and
   `pointer-strides.ti-O2.out` fault in SPMASK loops the same way.
6. **Cycle accounting** - no memory model at all, so `cycle.Total` cannot be matched (section
   1.5); `-c` counts from the entry point, not from `main` (`C6xHost.cpp:230`); no cross-path
   stall.
7. **The oracle kit** cannot find any of the above: sign-extended hex and a per-cycle vs
   per-packet step mismatch in the trace comparison, a decoder corpus that `dis6x` lists as
   data, and C-only programs linked without the EH library (section 1.6).
8. Cosmetic: `addSymbol` prefers `__TI_exidx_linkto_scn_start_N` over function names in
   diagnostics (`C6xImage.cpp:42`); CSR/IER/DNUM reset values differ from the simulator's
   (`C6xCpu.cpp:34`); `block == 0 || block == 0` (`C6xExec.cpp:145`); the repository's `build/`
   holds aarch64-Linux objects so `make` fails on the Mac.

The three patches used for the measurements (scratch copy only, not committed): MVC accepting
the `ILC` text operand; loads and stores executing in E1 (`last` ignores their memory and data
operands), the store's data captured then and the memory access kept in E3; nothing else.

## 5. Where the cycle counts diverge, and why

Not measurable yet (see summary). What is already certain from the model: the simulator
counts issue cycles only, so against `cycle.Total` it will read low by the L1D/L1P stall
component - on this map (everything in uncached SHRAM) the kernels' `cycle.Total` is several
times `cycle.CPU`; against `cycle.CPU` it should be within a few percent once D1-D5 are fixed,
less the unmodelled cross-path stall and whatever D4's loop-buffer timing error contributes.
